# Design rationale

Use only sections that help review this design. A small decision can fit in a paragraph.

## Problem and constraints

State the behavior to support, the actual caller, and constraints established from code and decision records.

## Caller usage

Show realistic inputs, outputs, failure handling, and the smallest useful call site before deriving the types.

## Shape and ownership

Name the domain data, signatures, module owners, validation boundaries, lifetime, and effects. Explain what complexity the interface hides and what callers still coordinate.

## Alternatives and choice

Compare genuinely different structures. Record the chosen one and the concrete cost accepted. If independent candidates were used, name the base and the ideas adopted or rejected.

## Proof and first implementation step

Name the observation that will establish the behavior and the first useful slice. Distinguish settled constraints from unknowns. Preserve design-only or stop-before-implementation requests.
